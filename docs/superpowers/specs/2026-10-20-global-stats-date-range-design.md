# 统计页全局日期范围与无限明细存储设计

## 状态

设计草案，待业主审阅。业主已确认：统计页需要统一日期选择器（预设范围 + 自定义日期）；统计事件与作品历史均需留存完整明细，不设条数或时间上限；使用本地 SQLite；系统诊断日志不属于本设计。

## 目标

- 页面顶部用一个日期范围选择器替代刷新按钮，支持近 7 / 30 / 90 / 365 天和自定义开始、结束日期。
- 同一范围统一控制指标卡、趋势、平台解析/下载、资源类型、作者解析/下载、按日热力图。
- 每次统计事件都有结构化明细，永久保留；不得用聚合计数或诊断日志替代事件明细。
- 作品解析历史永久保留，现有 5000 条持久化上限移除；页面按页加载，单次 IPC 不搬运全库。
- 日期按本机自然日解释，起止日均包含；未来日期不可选，开始日不能晚于结束日。
- 不存 Cookie、媒体直链或额外的隐私敏感诊断文本；原有历史字段按现有契约与隐私规则保存。

## 方案选择

1. **继续 JSON，追加无限事件数组**：不引入数据库，但每次写入/筛选都需要重写或扫描不断增长的文件；删除、分页、崩溃恢复成本会持续上升。拒绝。
2. **本地 SQLite 明细库（采用）**：事件与作品历史按行写入，索引支持日期、平台和作品查询；事务保证事件与历史一致，支持无界持久化与分页。迁移和打包/运行时适配需要一次架构改造。
3. **SQLite 加单独汇总快照**：查询更快，但增加第二份统计真源、重建与一致性复杂度。首版先以索引明细查询并聚合，确有性能证据后再加可重建缓存。

## 数据模型

数据库放在 Electron `userData`。建议至少有两类业务表：

- `history_entries`：现有 `HistoryEntry` 的逐条作品/下载历史，保留现有字段、唯一键/upsert 语义和删除语义，但不再截断旧行。页面需改为 limit + cursor/offset 分页；筛选与排序由主进程数据库查询完成。
- `stats_events`：不可变追加的每次统计事件，包括事件 ID、事件种类、事件时刻、归一后的平台键、资源类型、结果、字节数、传输时长及可空的作品引用。事件种类至少覆盖解析成功/失败、下载成功/失败/取消；每次解析请求均记一行，即使同作品重复解析或失败；每个下载任务终态记一行。

事件表只存统计所需字段，不写 URL、Cookie、文件名、作者名或媒体内容。成功解析和下载事件通过作品引用连接 `history_entries`；作者维度按所选日期内的作品引用去重，作者信息从作品历史读取。解析失败无法归属作者，按现有业务能力不纳入作者榜。若记录缺少作品引用，平台/总量仍统计，作者榜不虚构归属。

对 `stats_events` 建索引：事件时刻、事件种类 + 事件时刻、平台 + 事件时刻、资源类型 + 事件时刻、作品引用 + 事件时刻。历史表建作品键、平台 + 创建时间、创建时间索引。按日热力及其他分组均从同一个事件过滤结果聚合，避免各块口径分叉。

SQLite 驱动需在实现计划阶段根据当前 Electron/Node 运行时和 Windows 打包约束确认；优先采用随 Electron 运行时可用的 SQLite 能力，只有不满足并发/稳定性要求时才引入需原生重建的依赖。数据库启用事务和 WAL；每个事件落库与相关历史 upsert 在同一事务边界内，进程退出时正常关闭并完成 checkpoint。

## 日期范围与聚合口径

- 查询边界转换成本机自然日的 inclusive 起止；SQL 使用 `startAt <= eventAt < dayAfterEnd`，避免毫秒边界漏数。
- 默认近 30 天；选择预设后刷新全页。自定义日期通过日历区间面板选开始日/结束日，点“应用”后一次性提交；取消保留已应用范围。
- 主进程提供按范围的统计查询，renderer 不接收全量事件列表。`stats:get` 若改为接受日期范围或换为 `stats:query`，按 AGENTS.md 完成 IPC 六件套并升 `CONTRACT_VERSION`。
- 顶部四项卡片、总体趋势、平台解析/下载表、资源类型环图、作者维度、热力图都基于同一 `startAt/endAt`。
- 成功率分母为所选范围内成功 + 失败；取消独立展示，不进入成功率分母。解析失败率同理按解析成功与失败计算。
- 重复解析每次都进入解析次数；作者解析作品按作品键去重。下载按下载任务终态计数；资源文件数与体积按现有历史文件字段口径展示。平台/类型分组分别由事件字段聚合。
- 全部查询都需使用参数化 SQL；平台键走 `resolveKey()` 统一；不把 renderer 任意 SQL/表达式暴露给主进程。

## 旧数据迁移与覆盖范围

- 首次启动创建 SQLite 数据库，在单事务/可恢复迁移中将现有 `history.json` 中全部可读行写入 `history_entries`，保留解析作品 upsert 与下载明细；确认数据库提交成功后再将旧文件归档备份，迁移重复执行需幂等。
- 旧 `stats.json` 只有累计桶与有限的总量按日桶，无法还原每次请求、解析失败、下载失败/取消的时刻，也无法完整按平台/类型拆分。不得伪造旧事件或将累计值平均分摊到日期。
- 因此事件级日期统计从迁移后真实记录的首个事件时刻开始完整可查；早于该时刻的日期选择仍允许查看作品历史，但统计事件区块标注“统计明细从 YYYY-MM-DD 起记录”，早期事件指标为空/不完整，不显示成真实零。生命周期旧累计可以在迁移摘要中保留为“迁移前累计”单独值；不与新事件混加成看似精确的日期范围值。
- 旧 `stats.json` 可在成功迁移后保留为只读备份一段稳定周期；迁移失败时不删除或改写源文件，主界面明确报错并可重试。备份清理策略在实施计划里依据现有数据迁移/备份约定确定。
- 无上限指本机不自动按条数/时间删除业务历史和统计事件。用户主动删除作品历史时，按当前 `history:remove` 语义删除对应作品记录；统计事件是否保留是统计审计口径，建议仍保留，作品引用置空以保持事件汇总，而不通过移除历史回删统计事件。整库数据仅随用户主动清理应用数据而删除。

## UI 与性能

- 顶部日期选择器替代“刷新”；数据加载失败保留重试入口，正常刷新可通过当前选择器重新应用/提供轻量刷新动作，不额外增加重复日期控件。
- 移除总体趋势内部日期选择器；趋势数据类型、平台解析/下载、类型次数/字节切换保留。
- 全局日期范围标签只显示在顶部。图表无记录时延续现有局部空态；范围跨越事件数据起点时显示覆盖起点提示。
- 历史页采用主进程分页查询；搜索/平台/日期筛选和选择删除需能覆盖数据库全部历史，不能默默只操作当前页。全选删除由显式“选择全部筛选结果”语义处理，避免一次 IPC 传全库 keys。
- 数据无上限意味着库文件可随使用增长；查询必须走索引、历史分页、事件日期范围聚合，避免整库读入 renderer 或主进程内存。首版不设自动清理。

## 验收重点

- 注入同作品重复解析、解析失败、下载完成、下载失败、取消等事件，日期查询按天/平台/类型聚合与已知明细一致。
- 跨午夜、本地日边界、自定义单日区间和空日期区间边界正确。
- 迁移 5000 条历史和旧累计 stats 后数据不丢、不重复；中断后重跑幂等；源数据完整保留直至 DB 验证成功。
- 超过 5000 条后仍可分页看到最旧记录，跨页筛选/删除行为明确且不超 IPC 载荷限制。
- 事件与历史的写入事务失败时不产生“有汇总无明细”或相反的半条记录；重启后查询一致。
- 数据库内不存在统计事件 URL、Cookie、文件名或作者名；数据库和 migration 错误日志遵守隐私红线。
